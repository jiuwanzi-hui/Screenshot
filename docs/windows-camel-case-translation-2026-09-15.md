# Windows 驼峰词翻译修复

## 原因与改动

反馈选区中的 `TranslationModels` 被共用语言判断规则当成代码标识符，导致截图工具栏在调用模型前提示“已经是目标语言”。此外，短标题的宽松校验可能接受模型原样返回的驼峰词。

- 独立选中的 camelCase、PascalCase 和带前置缩写的复合词进入正常翻译流程，如 `translationModels`、`TranslationModels`、`HTTPServer`、`XMLHttpRequest`；共用规则同时覆盖括号、引号、末尾标点、下划线、连字符和独立文件名中的复合词。
- 仅在请求副本中加入词边界，`TranslationModels` 以 `Translation Models` 请求；语言检测使用同一副本。原 OCR 文字、坐标、分段顺序及失败后保留的原文不变。
- 在线模型、公共翻译及本机模型共用此预处理；公共服务先规范化再按请求长度限制分段。
- 驼峰词原样返回或只增加空格，不再计为成功的中文翻译，即便同批其他段落翻译成功。
- 完整路径、网址、账号、单独缩写和单位维持原有保护。独立文件名如 `TranslationProvider.cs` 的词干可翻译，请求保留后缀；正文中的名称和代码不按本规则拆词。带品牌前缀的描述性名称保留品牌拼写。
- 未改变用户的目标语言、提供方顺序或模型选择；仅修改 Windows，保留前一轮钉图修复。

## 验证

- Release 编译通过。
- 定向回归：137 通过、7 项环境依赖用例默认跳过；补充短标题、译文质量、补译及分段回归：70 通过、2 项环境依赖用例跳过。
- 单独启用本次截图的真实 OCR 到本机翻译测试：PP-OCRv6 Small 识别为 `TranslationModels`；TranslateGemma 4B 和 Hy-MT2 1.8B 均通过首次与连续翻译校验，译文包含“翻译”和“模型”。Hy-MT2 实际返回“翻译模型”。
- 本机 RTX 5070 Ti 上，Hy-MT2 此短选区 OCR 为 356 ms，首次翻译含加载为 2808 ms，连续相同输入为 16 ms；后者可复用推理缓存，不代表一般正文翻译速度，也不作为其他硬件的保证。
- 公共／在线接口使用受控 HTTP 响应验证实际请求文字、分段位置、原样返回拒绝及失败原文保留，没有消耗用户在线额度。
- 测试结束后检查无 `SnapCut` OCR、`llama-server` 或 `testhost` 进程残留。没有新增模型驻留或后台轮询。

未运行真实桌面输入集成测试；本次真实 OCR 使用用户提供图片的选区内部像素。

## 第二张选区与多种命名形式回归

- 新提供的选区在 `{496,42,154,50}` 和去掉边框后的 `{499,46,148,42}` 两组像素中，PP-OCR 均识别为 `TranslationProvider`。此前的纯驼峰规则在此图片上已经返回“需要翻译”，因此不能断言用户截图中的跳过提示由本轮补充的标点规则引起。
- 发现并修正了实际模型路径的另一处问题：TranslateGemma 在该短词源语言不确定时，原有长指令会输出到容量上限；对通用复合标签采用简短翻译指令，仍由模型判断语言，不猜定英语，不放宽完整性检查或更换模型。
- 最新 Release 定向回归 210 项通过，10 项依赖模型或环境的测试默认跳过；其中本次的 3 项实际模型测试另行启用验证。
- 两种模型均实际运行原图 OCR → 文字框收紧／段落合并 → 模型翻译 → 译文覆盖判定。Hy-MT2 返回“翻译提供商”；TranslateGemma 返回“翻译提供”，后者术语表达不够准确，流程通过不代表术语质量已完全解决。
- 另用两种模型逐项实际翻译 10 个不同形式：`ConnectionTimeout`、`getUserName`、`HTTPServer`、`XMLHttpRequest`、`user_settings`、`connection-timeout`、`(TranslationProvider)`、`ConnectionTimeout:`、`TranslationProvider.cs`、`UserSettings.json`。均进入模型并返回相关中文含义；不是只检查返回非空。
- 实际输出的限制：TranslateGemma 将 `TranslationProvider.cs` 译作“翻译服务”，没有保留 `.cs`；Hy-MT2 返回“翻译提供者.cs”。词干翻译入口已打通，译名和后缀保留仍受模型结果影响。
- 未新增常驻任务、设备探测、模型切换或重试循环；本轮未修改 macOS 和长截图算法。
