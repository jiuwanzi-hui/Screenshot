# Windows 钉图重复截图清晰度与关闭残影

## 范围与发现

仅修改 Windows 应用及其测试。未修改 macOS、长截图采集或拼接算法，未发布版本。

- 截图冻结画面原有 `BitmapCache`，给已有屏幕位图再增加一层栅格缓存。离屏复现时，在五档 DPI 中有四档出现黑白细线混色；移除缓存后五档逐像素一致。这个问题影响截图时看到的冻结画面，不代表保存路径一定使用了这份模糊画面。
- 单张钉图的边框阴影原来覆盖在图片上方，实际改变边缘附近的屏幕像素；再截图会把这些变化带到下一张图片。将其放到图片下方，保留外围边线和阴影。
- 钉图显示状态变化只刷新托盘菜单，没有使全局快捷键的菜单截图缓存失效。菜单缓存最长可保留 4 秒，可能包含已关闭的钉图。

当前代码已经保留钉图原始像素，并把输出比例延迟到复制／保存；本次继续保留这条路径。不能通过把输出改为 200% 修复已经发生的显示重采样。

## 修正

1. 冻结画面直接使用原屏幕位图，不再增加 `BitmapCache`。
2. 单图阴影置于图片下方，避免边缘像素反复变暗。
3. 钉图创建、关闭、最小化／恢复和编组状态通知均使旧缓存及其在途工作失效；新打开的菜单仍可正常缓存。失效通知不改变正在交接的截图输入状态。
4. 截图层或钉图改变后，下次快捷键首帧在原有后台采集线程中先调用一次 `DwmFlush`。连续通知合并，不增加常驻轮询或整屏缓存；继续受单一采集任务、取消、超时及迟到帧释放约束。

## 验证

- Release 编译通过。
- 使用反馈中的第一张 JPEG（676 × 162）以及逐像素彩色图案，模拟 100%、125%、150%、175%、200% DPI。
- 每个场景连续 10 轮检查冻结画面显示、未标注编辑器导出、完整钉图布局离屏渲染及下一轮取图；原图区域逐字节一致，覆盖阴影和边缘位置。
- 缓存回归覆盖旧菜单帧失效、迟到帧拒绝、新菜单恢复可用以及截图输入状态不被误清除。
- 后台合成回归覆盖多次通知合并、采集前执行、界面线程可响应以及后续无变化时不重复执行。
- 第一组相关回归：79 通过，26 按默认规则跳过（桌面集成或真实模型测试）。
- 第二组快捷键与截图交互回归：104 通过，3 项桌面集成跳过；两组有少量调度用例重合，不作为唯一用例数相加。

本次为离屏渲染与受控状态测试，未在反馈者的显卡／显示器上验证，也未把 JPEG 转发样本视为其无损原始截图。尚不能确认反馈中的全部模糊都来自同一原因；需要反馈者在当前构建复测，并补充版本、系统缩放与多显示器情况。未测量其硬件上的耗时、峰值显存或内存。

参考：[Microsoft BitmapCache 文档](https://learn.microsoft.com/en-us/dotnet/api/system.windows.media.bitmapcache)、[WPF 多显示器 DPI 示例](https://github.com/microsoft/WPF-Samples/blob/main/PerMonitorDPI/readme.md)。具体差异以上述本地回归为依据。
