# 4800H 工具栏渲染模式对照（2026-09-19）

## 当前结论

目标电脑的同版本对照已证明：强制 WPF SoftwareOnly 不能解决工具栏延迟。它缩短了部分隐藏准备时间，却增加实际显示时间；默认渲染路径保留，不据此自动切换软件渲染，也不改变 OCR、翻译或录屏编码的计算设备。

目前能分清两段等待：快速框选时仍可能遇到尚未完成的工作进程初始化；即使工作进程早已准备完成，窗口显示到可见交接仍有约 0.44 秒的固定后段成本。两轮隐藏布局候选已经完成本机同格式成品对照，收益不足以解释或消除目标机半秒以上的等待，相关 Capture 修改和专用候选测试全部撤回。

## 保留的修改和撤回原则

1. 中文是界面源语言。原来 `UiLocalization` 在中文首布局／Loaded 时仍逐元素建立状态和 `DependencyPropertyDescriptor` 观察器，并处理无须翻译的动态文本。候选修改在中文直接使用原文，不建立这些状态；只有显式切换语言时才遍历已有窗口和独立弹出菜单的根，随后由 Loaded／SizeChanged 处理新控件。切回中文恢复原文、原有文字方向并解除观察器。编辑框、用户正文和绑定数据的排除规则保留。
2. 录屏控制窗口使用普通窗口的 160 ms 透明度入场动画。候选修改只取消该工具栏首次交接的淡入，保留正常显示、布局、置顶和原生选区交接，不通过提前 Show／Hide 或遮蔽窗口制造准备完成的假象。
3. 隐藏布局两轮候选均已撤回，不保留提前连接根可视树、整页隐藏布局或关闭每像素透明的实验。不得只凭准备阶段某个计时变短交付，必须合并计算进程开始、松手、实际 Show、ContentRendered 和最终交接。

已有本机旧采样中，`UiLocalization.OnSizeChanged → Attach` 约 17.11 ms、`UiLocalization.Apply` 约 9.32 ms，表情渲染约 22.65 ms；这些采样有分析工具开销，且不来自本次目标机 A/B，不能据此宣称本地化开销解释了 4800H 全部等待。

录屏设备枚举已经放在工具栏交接之后；`InitializeSession` 中第二次 `InitializeComponent` 受生成代码的一次初始化标记保护，并非重复解析 XAML。不把这两处当作已确认的首显瓶颈。

## 后续线索：设置窗口最小化后仍能快速截图

用户补充：设置窗口打开时，即使最小化，截图松手后工具栏也快；没有设置窗口、功能进程空闲释放后则慢，连续截图未释放时快。截图中内存为 32 GB、3200 MT/s、可用约 15.1 GB。这些数字本身不能证明内存频率是瓶颈。

代码存在两个同时变化的条件，不能只称为“内存缓存命中”：

1. `App.FeatureProcesses.cs` 的 `IsFeatureWorkerBusy` 直接包含 `_mainWindow is not null`，不取决于设置窗口是否最小化。没有活动窗口／任务时，`FeatureProcessWorker` 约 2 秒空闲检查触发退出；`RetireFeatureWorkerAsync` 最终退出整个功能进程，释放 WPF／原生运行时资源。
2. `SendFeatureAsync` 仅在 `_featureHost.ProcessId is null` 时使用 `SendResidentSelectionAsync`。冷路径先显示原生框选层，松手后通过 `InitialSelection` 创建／显示 WPF 编辑层；已有功能进程则直接处理普通截图命令，由 WPF 截图层承载框选。因此暖路径的窗口首次显示发生在框选前，不能将其松手后计时与冷路径当作同一路径的纯内存带宽对照。

这条线索支持“功能进程生命周期＋两条截图路径的首次显示时机不同”，不支持直接归因于内存频率。运行时／图形缓存复用和流程差异各自贡献多少仍需分别控制条件；本节是源码核对及诊断修正，未改变程序、资源释放策略或测试包，也不宣称已解决目标机问题。

## 高回报率鼠标与低空闲内存的约束

用户进一步说明：原生边框／遮罩是为解决高回报率鼠标拖动不跟手而引入；如果 WPF 能保持跟手，允许使用 WPF，但仍要求工具栏及时出现和低空闲内存。

源码中的两种“原生”必须区分：`NativeSelectionFrameWindow` 是 WPF 截图窗口内部使用的边框／遮罩跟踪组件，设置已打开时的快速路径同样使用它；`ResidentSelectionWindow` 是功能进程不存在时先显示的独立原生框选界面，松手后再移交 WPF。不能把后者的冷交接等待当成前者的边框绘制开销，也不能据此撤销已解决高回报率拖动问题的原生跟踪。

`CaptureOverlayWindow` 在开始框选时调用 `StartSelectionTracking`，原生组件按帧读取最新物理鼠标位置，松手再次读取最终位置；WPF 鼠标事件在原生跟踪时直接跳过重复处理。现有 WPF 预览分支本身也已有按渲染帧合并更新的逻辑，不能把“增加节流”当成尚未存在且必然有效的修复。

评估方向应优先保留原生边框／遮罩，研究一次截图期间复用同一个 WPF 编辑会话、减少松手后的界面首次显示与交接。若继续空闲退出整个界面进程，下一次必然仍有初始化工作；提前至抓屏／拖动期间可能重叠等待，但快速松手仍可能等待。不能保证换回 WPF 即零延迟，也不能通过把等待搬到快捷键按下后、保持设置窗口打开或长期保留重型资源来宣称同时满足速度和低内存。验收必须分别测快捷键到框选、持续拖动跟随、松手到可操作工具栏，以及取消／结束后资源释放。
