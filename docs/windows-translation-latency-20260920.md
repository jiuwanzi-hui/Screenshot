# Windows 轻量翻译延迟与 4 GB 显存调度（2026-09-20）

## 用户证据与计时范围

GTX 1650 Ti 4 GB 用户已确认 Hy-MT2 1.8B 成功使用显卡。前三次对同一来源图片的不同框选显示 15.4、7.0、5.7 秒，另一张显示 7.1 秒；前两次详情分别为 2 路和 1 路。截图本身是译文结果，不能当作英文输入再做性能对比。

旧截图覆盖层计时从 OCR、版面分析之后才开始，包含翻译加载和推理，不含 OCR、最终排版。新的底部总时间从此次识别翻译操作开始，包含这些步骤，悬停详情分别显示识别／版面、翻译阶段、模型准备／加载与翻译／校验。翻译阶段包含模型加载，不能把这几项全部相加。这个时间到覆盖层提交为止，不是通过显示器光学测量的首帧时间，也不包含用户框选时间。

15.4 秒中究竟多少花在驱动、模型加载、正文推理或补译，旧截图不足以确认。不能断言是驱动损坏，不能把开发机结果等同于用户电脑，更不能承诺任意篇幅、首次启动都在 5–6 秒内。

## 已修正的代码路径

1. 按段落数判断“大截图”会漏掉标题加整块正文的 OCR 结果。全文超过 1800 字符时，旧的常规调度可先提交一个标题，按一个任务启动单路本机模型，后续正文沿用单路工作进程。现在长正文也交给整页调度，由所选本机模型分段并发。在线／公共／离线仍按用户顺序执行，保留失败片段、质量检查和回退原因。
2. 轻量模型不再套用较大模型的双倍权重预留。实际 b10276 / Hy-MT2 Q4_K_M / 两个 4096 token 上下文在开发显卡上的原生日志：GPU 权重 1075.74 MiB、KV 512 MiB、计算缓冲 24 MiB，合计约 1612 MiB；另有主机缓冲，不计作显存。新预算预留模型文件大小、每槽 384 MiB，以及固定 768 MiB；每槽实测 KV 是 256 MiB，其余是余量。4 GB 显卡当前预算约 2700–3500 MiB 时可保留两路，预算紧张时回到单路／原生 fit；不是看到“4 GB”就固定双路，也没有降低上下文或模型精度。较大模型预算、CPU 路径保持原规则。
3. 对固定 SHA-256 的 b10276 ZIP 编译入组件 SHA-256。每个新界面进程仍校验 ZIP 和已安装 DLL 的实际字节，但无需重复解压全部 DLL 来获取预期哈希。组件损坏仍从校验通过的 ZIP 修复；不信任可写的“已验证”标记。其他版本／测试 ZIP 继续走原校验路径。
4. 继续复用硬件配置缓存，不重复运行 Vulkan 探测。当前可用内存与 WDDM 预算按需读取；空闲 10 秒、取消、失败释放实际工作进程，没有增加后台模型驻留、预热或常驻日志。

## 验证

环境：Core Ultra 7 270K Plus、RTX 5070 Ti 16 GB、Windows 10.0.26200。不是 GTX 1650 Ti，限制显存预算也不能模拟该显卡算力。证据位于 `artifacts/windows-translation-latency-20260920`。

- `regression.log`：177 通过，2 个需显式环境开关的用例默认跳过。覆盖长正文与标题整页提交、提供方优先顺序、失败恢复、4 GB 有余量／紧张预算、驱动配置缓存、在线质量和语言路由等。
- `native.log`：8 个真实原生用例全部通过。包含 Hy-MT2 / TranslateGemma × GPU / CPU、实际中英翻译、取消后恢复、空闲约 10 秒实际退出、失败后释放、卡住探测恢复、跨会话硬件缓存；另覆盖可信组件哈希与 ZIP 逐字节对应、CPU / GPU 快速校验路径对同长度 DLL 损坏的修复。
- 两份不同英文正文，所选模型、4096 token 上下文、4 个 CPU 支持线程、600 字符分段与完整性校验保持一致。每组新建模型进程，按 A、A、A、B 顺序实测。A 为用户早先原始英文截图实际 OCR 文本（1636 字符）；B 从 README 不同录屏／OCR／翻译段落提取（2395 字符），不是复用 A 的译文。没有完整译文缓存，没有清空系统文件／驱动缓存。
