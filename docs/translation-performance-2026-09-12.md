# Windows 截图翻译性能验证（2026-09-12）

## 首次加载与硬件不足提示

同机、同模型、同三段中文转英文复测：首次启动进程及翻译由此前 2.99–3.27 秒降至本次 2.582 秒，已加载模型为 0.283 秒。两次输出一致，三段均通过完整性检查；耗时不含 OCR，也不代表系统冷启动或其他硬件的保证。未更换模型、精度、上下文容量、提供方顺序或质量检查。

原生进程分项对比表明：在显存和内存充足时，跳过额外的显存自动分配试算、直接加载至独显并使用缓冲读取，可减少首次等待。独立双次试验中，原路径从启动到三段译文完成约 2.75–2.79 秒，组合参数为 2.13–2.37 秒；此项不包含应用内语言判断和设备探测，不能与应用总耗时混为一谈。仅有足够独立显存余量时跳过自动分配，仅有足够可用内存时启用缓冲读取；核显、低显存及探测失败保持兼容配置。快速加载失败先恢复同设备的自动适配，再考虑 CPU。

本次进程实测峰值工作集约 1.65 GiB，三段冷、热翻译完成时分别约 0.72 / 0.78 GiB；这不是显存统计。原生试验及应用结果保存在忽略目录中的 `local-startup-*.json`，保留供性能对比核查；不进入发行产物。

离线执行前检查可用内存：严重不足时停止本机加载，显示可用量、建议余量及关闭占内存软件／切换在线或轻量模型的指引。显存受限、集成显卡或显卡失败回退 CPU 时显示可能较慢的提醒；检查设备、加载模型、生成译文及补译分别显示进度。覆盖普通截图、钉图及编组、长图结果编辑和文本翻译窗口，提示跟随主题，截图状态限制为两行并保留完整悬浮说明。文本翻译窗口另提供打开翻译设置按钮。按配置顺序回退后仍保留原始资源或加载失败原因，不能误报为译文质量问题。

321 项相关回归通过，默认跳过 12 项需真实服务、模型或桌面的测试。另显式运行三段冷／热基准，以及真实模型的日语文章和中、英、法、西、俄、阿 30 个互译方向，全部通过；取消首次加载、连续调用复用、空闲 30 秒退出、重启及取消生成的进程释放测试通过。低资源条件验证使用受控内存／显存预算；未在真实低配机器上承诺相同时延。规则已补充到项目习惯文档。

## 英文目标语言等待与钉图、菜单回归（18:57 后的修正）

用户新反馈的英文页面包含三段文字。修正前将相同三段英文、`auto → en` 送入当前 TranslateGemma 4B 路由，实测 7.94 秒后仍报“译文不是有效的目标语言内容”：短标题的语言置信度不足，原文被送去推理并在保持原样后被当成失败。这次复现没有包含在线回退，不能把 7.94 秒当成用户截图中 28 秒的完整分解。

钉图边线改为独立的像素条带，阴影仅作用于边线，图片不再经过整个窗口的效果缓冲。离屏测试连续缩小到多种整数／小数尺寸，检查图片内部像素不变，确认没有边线伸入图片；离屏旧实现未复现用户所示 GPU 尖角，实际桌面缩放仍需用户检查当前构建。

## 通用互译、公共服务与 OCR 复测

新增百度官方通用文本翻译，并把百度/有道归为单独的“公共翻译”类别。配置区放在离线模型之前，三种类别均可排序，已有在线/离线相对顺序保持不变。百度标准版每月 5 万字符、QPS 1；高级版每月 100 万字符、QPS 10，具体以账户权益为准（[官方接入说明](https://fanyi-api.baidu.com/doc/13)）。接口使用用户独立 APP ID/密钥、HTTPS 和官方 MD5 签名；密钥仍由 DPAPI 保存。服务版本控制批次与频率，测试使用真实翻译和完整性校验；没有百度/有道凭据，尚未实测这两个服务的真实时延。

目标语言下拉已加入普通截图和共用的钉图/编组编辑工具栏，和设置页、文本翻译窗口共用目标。切换后清除旧语言的覆盖层与缓存，异步返回的旧语言结果不会写回。

通用数字检查支持等值数量级、分组符号及 12/24 小时时间写法，例如 8300 万 = 83 million，下午 3 点 = 15:00。送入模型前展开带数量级的数字，避免让模型自行进行数量级换算。错误数字、遗漏数字和真实漏译仍会触发补译；在线分段格式错误也会进行有界补译，已通过的段落保持不变。

真实 TranslateGemma 4B 验证：中、英、法、西、俄、阿六种语言的 30 个方向全部通过（最终复测单段、已加载模型约 0.25–0.43 秒）。另用 5 段中文正文，包含日期、人数、8300 万数量和下午时间，翻译为英、日、韩、法、德、西、俄、阿，40 段全部通过。最终复测首个英语批次含进程加载 3.38 秒，后续语言批次约 0.72–1.11 秒；包含正文推理和必要修复，不含 OCR。不能将这些样本宣称为所有长页面一秒保证。

营销页截图（32 个 OCR 分段，含用户截图自带的工具栏文字）：在线 glm-4-flashx 最后一次翻译 1.40 秒、10 个请求，0 段未完成；离线热模型 1.03 秒，但含噪声的品牌文字有 1 段未通过校验，保留原文并提示，不能记为整页成功。此项计时在后续 OCR 改进之前取得，与上面的中文正文测试分开记录。

旧版 2.8.2 的本地模型是 Qwen2.5 1.5B，当前是 TranslateGemma 4B；旧版 `PreferFastProvidersForLargeCaptures` 还会在大选区且存在多个提供方时过滤掉 Qwen，走 Mozilla/在线路线。因此旧界面选择“千问”并不能证明当时一秒结果确实出自该模型。当前始终按所选顺序处理，并显示实际引擎。

### OCR 线程与像素传递

确认旧实现上限为 4 线程，而且预加载可能固化更小的池。现在按逻辑处理器数分档：1–2 使用 1 线程，4–8 使用 2，12 使用 4，16 使用 6，24 使用 8，32 及以上最多 12。预加载与识别使用同一预算。保留 PP-OCRv6-Small、1600 长边上限、词级框与识别阈值，不降低图像清晰度；使用 BGRA 行直接复制，移除 PNG 编码/解码。仍在空闲 30 秒后释放 OCR 引擎。

本机测试 2/4/6/8/12/16 线程、两张原图、各两次：所有识别文本一致。8 线程的收益最稳定，16 线程退步。

### 最终验证状态

Release 编译通过。本次 OCR、翻译、公共服务路由、配置同步、二维码和玻璃样式相关回归 354 项通过；真实模型及目标语言界面验证 5 项通过。完整 Windows 回归为 1403 项通过、77 项按默认规则跳过、1 项失败。
