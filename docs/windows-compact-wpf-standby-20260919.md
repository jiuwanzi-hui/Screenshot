# WPF 小工具栏待机尝试（2026-09-19）

## 范围与结论

本轮遵循用户要求，保留现有 WPF 工具栏功能、XAML、主题和操作，不改原生框选/长截图算法，不重写工具栏。仅修改 Windows。

尝试只预热工具栏后，首次截图前的 UI 进程确实较小，但执行完整截图后不能自动回到这个状态。因此尚未实现“用过之后长期只占小工具栏所需内存”。没有因某个冷启动样本较小就宣称已解决 100–200 MB 的问题。

当前生产代码保留一项独立、较小的改动：快捷键/Raw Input 的消息接收窗口改用普通 HWND_MESSAGE，不为完全不绘制内容的窗口创建 WPF HwndSource/HwndTarget。现有 WindowProcedure、热键注册、输入处理和 Dispatcher 顺序保持不变。工具栏本身仍使用 WPF，保持截图界面就绪的设置/进程生命周期策略未改。

## 小工具栏实验

隔离进程中将真实 CaptureToolbar 临时放到 1114.4×60 DIP 离屏 WPF 窗口，按现有资源绘制，再恢复原父节点。没有绘制代替可操作工具栏的图片，也未将反射/启动钩子加入产品。

- 预热后、首次截图前：UI 专用工作集 45.54 MiB，提交 105.61 MiB。
- 首次命令至交接通知 244.3 ms；第二、第三次 112.2/116.1 ms。
- 三次截图后空闲 35 秒：专用工作集 121.39 MiB、提交 218.37 MiB。额外预热窗口没有实现使用后的持续低占用，因此不部署这个候选。
- 这里仅将工具栏单独呈现；现有隐藏编辑窗口仍已构造。不能把它称为已经完成模块分离或只加载工具栏全部依赖。
- 另一个“截图结束后绘制小窗口以排空释放命令”的尝试，空闲专用工作集约 112 MiB，同样未显示改善，未部署。

窗口关闭/清理控件不等于卸载程序模块或所有原生分配器资源；.NET 可卸载程序集需要专门的可回收加载上下文以及引用清理，不能将当前默认加载的界面模块简单当成可随时卸载的缓存。参见 [微软程序集卸载说明](https://learn.microsoft.com/en-us/dotnet/standard/assembly/unloadability)。本轮没有使用内部 MediaContext 反射去改变产品资源生命周期。

## 消息窗口的同程序对照

同一个独立测试程序分别创建旧 WPF 消息窗口与新普通消息窗口，每种三次独立进程。均先执行相同 WPF 渲染兼容性选择，不创建可见界面、不注入输入。以下为创建后 1 秒的样本范围：

| 指标 | WPF 消息窗口 | 普通消息窗口 |
|---|---:|---:|
| 创建耗时 | 34.32–36.84 ms | 4.71–4.90 ms |
| 进程专用工作集 | 22.59–23.00 MiB | 15.24–15.50 MiB |
| 进程提交量 | 53.50–54.13 MiB | 37.30–38.20 MiB |
| 线程数 | 25 | 14 |

这是单一消息窗口的隔离对照，不等于 SnapCut 截图后的整进程能够再省同样的内存：真实工具栏和悬浮按钮仍会按需加载 WPF。实际修改后源码工作进程三次截图、空闲 35 秒仍约 84.73 MiB 专用工作集，提交约 148.10 MiB；此外还有常驻进程，不能与用户任务管理器组内存混用。

另一次启用原有窗口准备和提前像素传输的源码实验，首轮交接 287.9 ms、后两轮 175.0/138.9 ms；空闲 35 秒为 90.72 MiB 专用工作集、152.12 MiB 提交。由此不能宣称已把完整截图后的 UI 进程压缩到约 45 MiB，也不能根据这些本机样本保证 4800H 首次无感。

上一轮发布程序的其他实验提交约 181 MiB，但程序打包形式和运行条件不同，不能直接将全部差值归因于本次消息窗口修改。以同程序对照和真实生命周期检查分别判断。
