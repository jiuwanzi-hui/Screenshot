# Windows 玻璃主题切换刷新

## 问题与调整

反馈：普通主题切到“清透琉璃”后，控件颜色已更新，窗口仍像白底；截图触发窗口重新显示后才透出底层内容。

此前的性能优化把色板批量更新、主题通知和原生窗口材质刷新放在同一同步调用中。后续布局／重绘仍可能更新 WPF 原生绘制底板，因此这一顺序没有保证透明材质是本轮界面更新的最终状态。

`AppThemeManager` 保留即时、批量的色板发布，把原生材质及文字保护的单次刷新放到 `DispatcherPriority.Loaded` 阶段，在当前布局／重绘之后提交。连续主题选择取消前一个待执行刷新，只采用最新主题；窗口集合在执行时读取，不捕获已关闭窗口。已有待执行刷新时，窗口 Loaded 不再重复执行同一遍材质处理。主题管理器释放时取消待执行操作，已释放的管理器忽略迟到请求与 Loaded 事件。

没有新增定时轮询、截图、窗口重建或隐藏／显示操作；未改主题色板、玻璃透明度、截图内容和 macOS。

## 验证范围

- Windows Release 编译通过，主题及材质相关回归 **129 通过，0 失败，0 跳过**。
- 在隐藏 HWND 上连接真实设置窗口控件树，使 Loaded 和主题卡片处理函数实际运行，不显示桌面窗口。依次选择普通浅色、普通深色、两种玻璃主题，核对保存的主题、最终背景画刷、原生绘制底板透明度、窗口句柄不变及窗口始终隐藏。
- 增加明确的故障注入分支：在 Render 阶段将绘制底板设回不透明白色。临时恢复旧的同步提交方式时，该分支失败，得到 `#FFFFFFFF`；新提交顺序恢复为透明并通过。没有注入的分支在新旧方式下均通过，因此不能声称已在测试机自然复现用户桌面的白底现象。
- 连续切换只保留最终主题，释放主题管理器取消排队刷新。既有回归检查色板只发布最终画刷、普通主题恢复、窗口文字与玻璃控件对比、托盘／弹窗材质、截图选框主题和选中动画。

## 性能与限制

本机独立运行设置卡片回归，首次切换约 39.8 ms，后续约 6.0–19.2 ms，包含设置处理、布局和原生材质提交。纯色板与离屏布局测试约 4–11 ms；两组计时范围不同，不能混用，也不代表低配硬件或真实桌面合成耗时。

没有运行真实桌面抓屏／输入集成测试。用户截图中的实际透底效果仍需在本次 Release 上直接切换确认；离屏透明度测试不等同于所有显卡／Windows 桌面组合的视觉验收。
