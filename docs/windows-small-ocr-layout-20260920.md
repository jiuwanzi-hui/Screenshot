# Windows small OCR、翻译字号与等待优化（2026-09-20）

## 用户反馈与复现

用户 GTX 1650 Ti 4 GB / 4800H 截图显示：OCR／版面约 3.4 秒，Hy-MT2 准备
1.8–3.6 秒、翻译／校验约 4.9 秒，总计 10.7–12.4 秒。该设备没有连接到本次
开发环境，不能用开发显卡的速度承诺这台机器首次／所有图片都在 5–6 秒完成。

输入使用用户提供的**英文原图** `codex-clipboard-220e939b-8cd6-446b-85ff-ffa0b7b7a4c6.png`，
裁选 `(80,65,1064,676)`，不把译文截图当英文 OCR 输入。证据保存在
`artifacts/windows-small-ocr-layout-20260920`，图像只在本机测试，未上传。

小字体已实际复现：不同高度的行内代码按 Y 排序后未能与左右正文合并；画布又以
**整段高度的 12%** 判断段落是否接近，并采用所有合并块中的**最小字号**。
这使多段文字连锁合并到一个大框，全部向顶部挤。修复包括：行内片段双向、传递
合并并按 X 排序；句末与段落间距判断；画布相邻阈值使用字号；重叠块保留主要
正文的字号。多行 OCR 框的墨迹分析也不再把完整文字压成中央一行。

真实 OCR → Hy-MT2 → WPF 离屏输出已核对：三个段落各在原有位置，实际字号
约 21.5–23.1；包含行内代码、小字、段落间距与中英文字。并未通过统一放大字体
或删减译文掩盖错误。见 `layout-before.png` 与 `overlap-after.png`。

## 识别优化

Windows 使用 `Screenshot.OcrRuntime`，源自 RapidOcrNet 3.0.0 的固定提交
`590d44b2efc7ecbef446c36bb6359ebbfcffeb50`，保留 Apache-2.0 头和完整许可证，
在包内提供 `Licenses/RapidOcrNet.txt`。Mac 项目仍使用原依赖，没有修改。

- CTC 在连续分数内存上进行 SIMD 最大值扫描，保留第一个并列最大值、NaN、
  空白符与重复字符语义，避免每个词表项的多维张量索引；非连续布局保留原实现。
- 多行使用同一 ONNX 会话及其线程池并行，不为每行另开一组线程；保留原裁剪
  宽度，不采用会改变识别输出的补齐批量。任务结果仍按原检测顺序返回。
- 线程预算 ≥10 且可用内存 ≥8 GiB 时最多三行，≥4 且 ≥4 GiB 时最多两行；
  更紧资源／未知内存保留单行。模型、精度、分辨率、阈值和坐标算法保持不变。
- 截图详情新增 OCR 进程准备、模型准备、实际识别、线程与行并发，便于区分
  推理时间与界面／截图准备；不写常驻性能日志。

## 翻译等待

点击翻译后允许 GPU 模型加载与 OCR 重叠，仅限配置中离线排第一、选择相应
本机模型、有有效硬件缓存、独显可直接容纳模型、可用 RAM ≥8 GiB、至少六个
物理核且当前负载有余量。缓存缺失时不为此运行 Vulkan 探测；CPU／显存不足
保留正常串行加载及回退。没有提前调用排在用户优先方式之后的提供方。

准备工作使用独立操作标识。空图、取消或无需翻译时只结束本次未被实际翻译
使用的进程；其他操作不能取消它。实际翻译接管后按原 10 秒闲置期限复用、退出。
截图 OCR 和翻译都传递生命周期取消令牌，避免只取消界面等待而让原生计算继续。
没有开机预热、长期模型驻留、定期唤醒或清空工作集。
