# Windows 普通截图空闲后工具栏准备

日期：2026-09-18。保持版本 4.1.5，仅修改 Windows 普通截图的工具栏准备和交接；未发布或替换发行包。

## 问题与处理

用户反馈 Ryzen 7 4800H 电脑主要在空闲后第一次框选、松手后等待工具栏。原路径会在原生框选期间构造、布局、关闭一套默认截图窗口，松手后再按用户配置构造正式窗口。前一次布局还将工具栏移出原窗口，失去其资源上下文，不能直接复用实际控件。

第一版改为在当前框选期间，使用当前设置准备正式窗口的实际控件树、模板和布局。当时暂不创建编辑器 HWND、不显示窗口、不抓取新屏幕；松手后接入原始截图和选区，直接使用同一个工具栏及原生辅助窗口。设置快照或显示器范围改变时丢弃准备结果，走正常构造路径。保留首帧完成及桌面合成确认后才交接的流程。后续收到真实耗时日志后，进一步将隐藏 HWND 的创建提前至当前框选期间，见下文。

取消、切换其他操作、功能进程退出时关闭准备窗口。准备阶段选择首个可见标注工具不再触发设置保存，避免无操作却改变配置并使准备结果失效。准备对象只属于本次活动的功能进程，不在常驻快捷键进程中保留。维持结束后约 2 秒的功能进程退出边界，无工作集清空或强制 GC。

为比较同一台电脑的首次与连续截图，增加进程启动、管道连接、命令接收与派发、原生松手、工具栏准备与复用、编辑器内容首帧、桌面合成确认和交接完成时间点。日志包含进程号、线程号和同机可对齐的高精度时钟，按进程分别写入 `capture-timing-{进程号}.log`，避免两个进程争用同一个追加句柄导致日志写入停止。写入在后台合并，每个文件超过 5 MiB 时轮换一次。

## 收到日志后的隐藏窗口准备与系统菜单修复

证据来自用户提供的 `installer/dist/Diagnostics`，以及 `152cf90d99838bc8d655a42590838eb7.mp4`、`885ff71868b81755d16450e11fc1b8d1.mp4`。用户补充操作为按 Shift 右击打开 Windows 旧式菜单，再按 F1 截图。视频中的报错明确为截图窗口未取得输入焦点。原程序只尝试一次激活；菜单仍占用输入时没有退出菜单模式的交接路径。

处理顺序现在是：后台取得并保留带菜单的原始屏幕像素，再识别当前前台线程的菜单状态；仅向该菜单所属窗口及捕获窗口投递 `WM_CANCELMODE`，异步等待菜单释放输入，再激活截图层。总等待最多 350 毫秒，支持取消；前台切换到其他窗口时停止接管。普通窗口不接收取消菜单消息，不使用全局 Esc，也不在生产代码中附加其他程序输入线程。普通截图的 WPF 首帧路径与常驻原生选择器共用此处理。

诊断日志的三次原生框选均已在松手前准备完工具栏，并复用了准备对象。分段情况如下（同机 QPC／时间点对齐）：

| 松手时间 | 松手至交接完成 | 编辑窗口 Show 调用 | 行内编辑器初始化 |
| --- | ---: | ---: | ---: |
| 10:00:58.052 | 约 553 ms | 约 230 ms | 76.7 ms |
| 10:01:12.645 | 约 555 ms | 约 231 ms | 85.1 ms |
| 10:01:22.173 | 约 542 ms | 约 230 ms | 83.1 ms |

因此进一步将真正的隐藏编辑器 HWND 和边框辅助 HWND 创建提前到本次活动框选期间。它们不显示、不激活，也不再次抓屏；接收选区时复用同一窗口，补上实际显示器位置和原生覆盖层所有权。首帧初始化期间合并反复提交的边框、遮罩及尺寸位置，只发布最终状态；选区拖动仍即时更新，长截图流程没有使用这个合并范围。初始化中关闭时不再发布已取消窗口的原生画面。对象继续属于按需功能进程，退出后释放。

同时将遗留在全局键盘钩子中的原始键码记录移至独立输入诊断开关。测试包仅记录阶段耗时，常规 Release 不启用这些耗时记录。

验证结果：

- Windows 相关非桌面回归：130 项通过，6 项桌面用例按默认跳过；Release 编译成功，既有分析器警告保留。
