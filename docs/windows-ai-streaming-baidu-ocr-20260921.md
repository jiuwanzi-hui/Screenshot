# Windows 问图流式输出、百度大模型翻译与四核 OCR

日期：2026-09-21。沿用 4.1.8，本地开发验证；没有正式发布，没有修改 macOS 或长截图算法。

## 问图

聊天接口改为 `stream: true`，按 SSE 增量显示回答；兼容服务实际返回的 `reasoning_content` / `reasoning` 文本单独显示在“处理思路 · 模型返回”中。处理时展开，结束或停止后收起，可手动展开。没有返回思路的模型仅显示回答，不编造内部过程；当前使用 Chat Completions 兼容接口，并不代表所有服务都会提供 Codex 式推理摘要。

网络读取在后台，响应上限 2 Mi 字符；界面每 80 ms 取最新快照，避免 token 回调堆积。用户向上阅读时不强制滚到底部。停止、中断与截断保留已收到的文字，未完成内容不作为成功回答写入后续历史。输入草稿、排队和调整方向继续有效，结束后停止刷新计时器。

接受只返回 JSON 的兼容服务。仅当 HTTP 400/422 明确拒绝 stream 参数时，按原模型和内容重试一次非流式；不因鉴权、图片能力错误或生成中断重新发送图片。

依据：[OpenAI 流式响应文档](https://developers.openai.com/api/docs/guides/streaming-responses)。第三方 reasoning 字段为兼容扩展，不视为 OpenAI Chat Completions 保证提供的字段。

## 百度大模型文本翻译

设置 → 翻译 → 添加公共翻译，服务类型增加“百度（大模型文本翻译）”。它和原百度通用翻译分开保存，使用 APP ID + API Key，接口固定为 `https://fanyi-api.baidu.com/ait/api/aiTextTranslate`，JSON 请求使用 `model_type: llm` 和 Bearer 鉴权。此服务不出现在图片问答模型列表。

保留用户的提供方顺序，整页批量、原文对应、数字和目标语言检查；缺失段落保留原文并报告失败。单批不超过 1900 字符，默认保守限速 1 次/秒，不把控制台体验额度当成永久免费。实际请求失败/恢复反馈到该配置的状态。模型测试实际请求两段翻译并校验，用户密钥继续独立加密保存。

官方依据：[产品页](https://fanyi-api.baidu.com/product/13)、[平台接入文档](https://fanyi-service.baidu.com/pub/richText/e/eb0a24364f4915ede18b882e15aa0902)。该文档由百度平台前端引用：要求 APP ID、支持 API Key，默认 llm，建议 2000 字符内，上限 6000。不是百度智能云另一套 access_token 接口。

验证使用模拟 HTTP 响应；未使用用户账户调用付费接口，真实账户开通、额度和线上延迟仍需在配置页测试。

## OCR 证据与限制

用户反馈 i5-7500 / 16 GB / RX 470 4 GB，每次约 20 秒，未同时运行其他模型。尚无该机分阶段数据，不能认定 CPU 争抢，也没有宣称该机 20 秒问题已修复。

发现原预算将无 SMT 的四核 CPU 也限制为最多 2 个线程。现仅对四个物理/性能核心、四个逻辑核心、AVX2、可用内存至少 4 GiB 的机器允许 3 个线程，仍受当前 CPU 负载限制；不改翻译线程预算、模型、分辨率或识别阈值。

本机是 Core Ultra 7 270K Plus（24 核 / 24 线程），不是 i5-7500。以用户视频中的 976×832 设置页面作为样本，进程 affinity=15 限四个逻辑处理器，固定行并行=1，保持 Small、相同分辨率与文本框设置：

| OCR 线程 | 第一次识别 | 连续识别 | 与单线程文字一致 |
| --- | --- | --- | --- |
| 1 | 2.84 s | 2.51 s | 是 |
| 2 | 1.47 s | 1.54 s | 是 |
| 3 | 1.13 s | 1.13 s | 是 |
| 4 | 0.97 s | 0.92 s | 是 |

该对照只支持四核预算调整，不能模拟 i5 的架构、内存、磁盘及软件环境，也不能承诺它达到相同时延。保留一个核心余量，没有选择全部四线程。

同样本完整工作进程路径，本机未限制核数时：首次 0.80 s，连续 0.44 / 0.44 s。结果文字、行框和词框与修改前完全一致。首次包括进程约 0.05 s、模型约 0.20 s、识别约 0.48 s。未触发 Medium 增强。

OCR 结果弹窗底部及悬停说明新增总时间、图像尺寸、排队/预准备等待、进程准备、模型准备、识别、CPU 线程/行并行，以及实际调用 Medium 时的增强耗时。统计随本次结果传递，不增加常驻探测或杂项日志。下一步用目标机这里的明细判断 20 秒属于启动、加载、推理还是增强处理。

## 验证

- Release 构建通过。问图/图片模型/百度/资源预算/设置回归 126 通过，6 个真实桌面集成测试按约定跳过。
- 流式测试覆盖完成前展示、思路与答案隔离、继续输入、停止保留文字、提前断流、服务错误、JSON 兼容和明确不支持流式时的一次回退。
- 三种主题离屏布局验证通过，并检查玻璃主题、窄深色窗口渲染。
- 本机原生 OCR 与工作进程回归 9 通过：像素传输、首次/连续/再次加载、取消后恢复、无效模型失败退出，以及空闲约 10 秒后进程实际退出。父进程未加载 ONNX。
- 小图生命周期样本：冷启动 372 ms、连续 33 ms、空闲后再加载 372 ms；工作进程总工作集约 164.1 MiB、峰值总工作集 164.4 MiB、私有提交 123.0 MiB，随后进程退出。不同样本和硬件不能套用这些数字。
