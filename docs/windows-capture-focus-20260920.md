# Windows 弹窗上方截图与输入交接（2026-09-20）

## 问题与修正

用户提供 ToDesk“无法找到入口”弹窗照片：SnapCut 遮罩／选框处于报错窗口下面；随后提示“截图首帧尚未接管鼠标输入”。ToDesk 的入口错误属于被截取应用，本任务处理 SnapCut 的窗口顺序与输入交接。

原实现存在两个直接问题：

1. `TOPMOST` 仅表示置顶窗口组，不能保证排在组内已有弹窗之上。窗口已获得前台时，原激活帮助类直接返回，未重新排到已有置顶弹窗之上。
2. 普通窗口只尝试一次激活并立即检查前台；WPF 初始交接进一步将“前台不是自己”直接等同于无法框选。这会把暂时拒绝／尚未完成的键盘焦点转移当成截图失败，即使鼠标已经可以安全落在截图层上。

修改后的流程仍先取得原始屏幕像素，再显示截图层；随后仅调整本程序截图 HWND 的置顶顺序。焦点激活最多两次、总计约 350 ms；若前台已被用户切到其他窗口，取消此次交接。普通成功路径无需等待该上限。

完整可见且可接收鼠标的截图层，可以直接开始框选，不以键盘焦点暂时未转移作为退出条件。输入验证检查每个显示器中心、当前鼠标以及前台窗口与截图区域的交集中心，并检查前台线程的鼠标捕获／活动菜单；`WindowFromPoint` 单独成立不能证明鼠标未被其他菜单捕获。若窗口仍被遮挡、鼠标仍归其他窗口捕获或透明表面未呈现，不冒充输入就绪。验证期间只恢复一次输入窗口顺序，再按原有条件考虑一次 WPF 局部渲染恢复，不全局关闭硬件加速。

WPF 沿用已有 Esc／C 全局取色处理。原生选择层仅在 Windows 未给前台、鼠标表面已经就绪的兼容路径增加临时键盘转发，只接管 Esc／C；钩子仅投递私有窗口消息，实际取消／取色在 UI 消息循环执行，不在输入钩子里同步截图、写盘或访问剪贴板。隐藏、结束或取消时释放钩子，正常获得前台的路径不安装此钩子。私有消息避免 WinForms 的对话框预处理吞掉 Esc。

最终仍无法接管鼠标时，错误改为说明画面未呈现／被遮挡，错误日志的内部异常记录前台 HWND、进程 ID 与鼠标命中窗口、扩展样式，不读取弹窗文字或采集新图像。没有关闭 ToDesk 弹窗、降低其他窗口的置顶状态、附加其他应用输入线程、模拟全局 Alt/Esc、改任务栏或申请管理员／UIAccess 权限。

## 验证与范围

- 相关 Windows 回归 147 项通过、7 项依赖真实桌面输入／呈现的测试按项目约定跳过。
- 新增 4 项隔离桌面原生验证：建立从不切换为输入桌面的私有 Windows 桌面，验证已有置顶弹窗的前后顺序、鼠标命中截图 HWND、弹窗样式及截图几何不变，以及 Esc／C 异步转发与钩子释放、其他窗口仍捕获鼠标时不误判就绪。没有在用户桌面显示测试图案或注入全局输入。
- 隔离测试最初的 STA 线程自带 OLE HWND，导致无法切换桌面；改用只创建原生窗口的 MTA 专用线程。测试还发现合成 `WM_KEYDOWN` 的 Esc 被 WinForms 预处理吞掉，因此产品改为私有消息。这两处均已复验通过；专用线程退出后关闭私有桌面，避免遗留句柄。
- Release 编译只有既存 OCR／设置分析器提示。没有修改 macOS 或长截图采集／拼接算法。
- 未在用户那台电脑复现其实际 ToDesk 系统错误框；隔离验证覆盖普通置顶弹窗与焦点拒绝路径，不能宣称覆盖所有系统特殊窗口层级。目标机需用最新临时包在原报错场景复测。
