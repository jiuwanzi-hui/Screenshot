# Windows 空闲唤醒、取色面板与 Medium OCR 修复

本次继续使用 4.1.7-localtest，不递增本地测试包版本。只修改 Windows 路径，不发布正式更新。

## 原因和处理

- 冷启动框选由驻留进程的 GDI 窗口显示，热启动由 WPF 显示。原生取色面板原来是竖向简化布局、13×13 采样，缺少 RGB。现在使用横向 112 DIP 放大镜、25×25 采样、HEX、RGB、操作提示和主题边线；支持 DPI 缩放、屏幕边缘与增量重绘。原生 GDI 与 WPF 的文字和玻璃材质渲染仍有技术差异，不宣称逐像素一致。
- 功能进程和 OCR 子进程原来在调用方同步执行 Process.Start，冷启动安全检查、映像加载会占用处理低级输入钩子的界面线程。改在后台创建进程，保留身份验证、取消、退出和异常清理。功能进程完成主题初始化后才安装低级钩子；启动反馈窗口首次布局期间使用鼠标钩子暂停租约，布局完成恢复。
- OCR 改成独立工作进程后，已有 PrewarmAsync 在非工作进程直接返回，框选期间的提前准备失效。现在仅用户主动开始 OCR/翻译框选时，通过当前用户私有管道要求子进程加载已安装模型。普通待机不加载，主进程不加载 ONNX。首次识别仍需分配实际输入相关的推理资源。
- 已准备的会话与识别共用同一线程预算；子进程恢复正常调度。未使用的准备在框选取消后结束，实际识别取消可终止工作进程，连续识别短暂复用，空闲约 10 秒实际退出。没有改成常驻模型或清空工作集。
- 工具栏主动 OCR 在构建结果提示窗之前开始识别，使子进程准备与窗口创建重叠。
- RapidOcrNet 3.0.0 对高宽比超过 1.5 的检测框按横卧文本旋转，原始竖排艺术字会被当成侧向文字。对低置信度、接近竖直且大小受限的候选列，使用原图像素按几何推导的字数临时横排再识别。最多尝试 4 列；只接受完整 CJK 字符、置信度至少 0.8 且提高至少 0.15 的结果。输出仍采用原有 0.45 门槛。字符框映射回原图，不更改截图或使用样图固定坐标、文字答案。

## 验证范围与限制

- 真实反馈图为 235×321；新共用识别路径输出“牛兔鶏”“鼠虎猴”。原先的“房”类结果消失，但“鶏”与源图最后一字的繁体字形仍不一致。不能保证艺术字、繁体异体字全部正确，也未做字形强制替换。
- 覆盖真实模型首次、连续、空闲再次加载、准备复用、取消、错误模型、进程退出、父进程未加载 ONNX，以及小图中英文、深浅背景、彩色字、空白和字符坐标。模型测试通过环境变量指定本机文件；不把用户图片加入仓库或发行包。
- 取色面板按 100%、125%、150%、200% DPI 离屏渲染，验证采样位置、屏幕边缘、旧面板擦除、原图不受影响与资源释放。测试图不显示到用户桌面。
- 自动测试不能代替反馈者电脑的实际鼠标响应、截图工具栏交接闪屏与重启感受验证。未运行默认关闭的全局输入／顶层窗口桌面集成用例。
- 当前机器的性能测量不是旧电脑的速度保证。Medium 本身计算量更大，冷启动优化不能保证所有图都达到 Small 的耗时。

最终测试数量、实际耗时、包大小及 SHA-256 记录于 [4.1.7 本地验证记录](releases/4.1.7-localtest-validation.md)。
