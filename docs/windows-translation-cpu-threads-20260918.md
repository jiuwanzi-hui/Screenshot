# RTX 5070 Ti 翻译的 CPU 线程数实测

2026-09-18。用户询问界面显示“4 个 CPU 线程”是否太少、能否通过增加线程加快 TranslateGemma 4B。

## 核对结果

本机通过 Windows 查询到 Intel Core Ultra 7 270K Plus，24 个核心、24 个逻辑处理器。当前显卡是 RTX 5070 Ti。界面的“4 个 CPU 线程”是传给 llama.cpp 的 `-t` 计算线程预算，预填充的 `-tb` 也是 4；不是系统只有四核，也不是把整个程序限定到四核。应用没有因此设置 4 核 CPU affinity。

完整显卡路径通过 `--device Vulkan0 -ngl all` 将可卸载模型层交给独显；CPU 仍负责主机端计算及调度。当前本机资源规则根据性能核得到 4 个 CPU 线程、8 路并发。OCR 使用另一套预算，在此前这台机器的实测中为 12 线程，CPU 翻译路径也有独立预算。

[llama.cpp 官方参数说明](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) 将 `--threads` 定义为生成使用的 CPU 线程数，将 `--threads-batch` 定义为批量及提示词处理线程数。[官方性能排查说明](https://github.com/ggml-org/llama.cpp/blob/master/docs/development/token_generation_performance_tips.md) 也要求按实测选择线程数，过多线程可能降低速度。这两份资料仅作参数背景，本次结论以当前安装的 b10276 Vulkan 运行库实测为准。

## 对比方法

新增可选择运行的 `TranslationCpuThreadBenchmarkTests`。使用之前用户网页的固定 67 段英文 OCR 输入，统一 TranslateGemma 4B Q4_K_M、RTX 5070 Ti、8 路并发、32768 总上下文、相同批量、提示词、精度及完整性验证。复用应用实际的提供方、语言过滤、补译逻辑和原生请求实现；只在测试中改变原生服务 `-t`、`-tb`，没有修改产品默认配置。

顺序为 4→8→12→16→4，每档新建模型服务，记录一次首次翻译和两次连续翻译。结尾重复 4 线程以检查顺序与缓存影响。所有 15 次结果均通过现有完整性检查、无失败片段，均自动补译一个未完成片段。各档结束后退出本次测试的原生工作进程。测试仅使用本地模型和环回连接，没有调用在线翻译。

| CPU 线程 | 连续样本数 | 连续平均 | 连续范围 |
| ---: | ---: | ---: | ---: |
| 4 | 4 | 4.143 秒 | 4.117–4.184 秒 |
| 8 | 2 | 4.432 秒 | 4.136–4.727 秒 |
| 12 | 2 | 4.365 秒 | 4.327–4.403 秒 |
| 16 | 2 | 4.191 秒 | 4.089–4.293 秒 |

独立模型加载约 1.92–2.12 秒。最后重复 4 线程：加载 1.999 秒，首次正文 4.131 秒，合计 6.129 秒；接着两次正文为 4.184／4.117 秒。首次包括新建模型进程，但系统文件缓存未清空，不称为整机冷缓存启动。耗时不包含这次没有重复的 OCR 和桌面渲染。

## 结论与范围

增加至 8／12／16 线程没有稳定收益，没有理由只为了提高显示数字而改变产品默认值。保持 4 个 GPU 路径 CPU 线程；本轮未重新打包，现有 4.1.7-localtest 包未改变。不能据这组小样本断言 8 线程永远更慢，也不能推广到 CPU 单独运行、显存不足混合运行或其他电脑。这里的完整性通过不代表每个专业术语的翻译都完全正确。

证据保留在 `artifacts/translation-cpu-threads-20260918/comparison.json`、`comparison.trx` 和日志中。没有新增模型副本或解压目录。测试完成后重新启动源码 Release，具体 PID 与路径见同目录 `source-launch.json`。
